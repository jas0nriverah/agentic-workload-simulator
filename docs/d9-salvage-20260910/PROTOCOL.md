# D9 retained-evidence completion protocol

Authority: original `Coding tests Harrdware (2).pdf`, Step 3 and Deliverable 9. The literal acceptance condition is every individual event and E2E within 25%; coverage is a diagnostic, not a substitute for this condition.

## Scope and comparisons

This pass improves the offline simulator only. It does not change acquisition, allocate GPUs, resume the incomplete production matrix, or reopen D1–D8 acquisition. Historical tool-wall, request-proxy-wall, repaired native phases, individual CPU operations, and lifecycle spans remain different targets.

1. Reuse the authorized historical training view, retaining its instance-grouped outer folds and historical access disclosure. Compare at most four prespecified conditional GPU models. These are development cross-validation results, not a fresh sealed test.
2. Inventory accepted repaired attempts by identity before opening event labels. Derive eligibility from the pinned split. Keep confirmation/final-evaluation instances excluded from fitting. Preserve all repetitions of each instance within one fold. Do not select successful model outcomes or short trajectories.
3. Reconstruct eligible repaired evidence using identity-bound raw journals. Reject invalid CPU loss, physical-request joins, or hardware-domain bindings. Report excluded or inaccessible evidence with reasons; do not quietly change denominators.
4. Fit mechanism-specific native/lifecycle models where independent support permits. CPU operation latency and command wall must not be interchanged. Unsupported event classes stay explicitly unsupported.

## Prediction contracts

**Prospective:** inputs available before the predicted event; no realized output tokens, current event durations, measured residuals, or future state. Previous observations may be used only with a separately validated sequential protocol.

**Trace-conditioned:** a workload supplied to the simulator may declare token counts and event descriptors. Realized output length from a recorded workload is allowed only under this explicit conditional contract. This is not a forecast of the agent's future token count, action sequence, outcome, or execution time. No timing target or measured residual is a predictor.

## Metrics and selection

Report event count, independent instance count, within-25% coverage, p95 relative error, worst relative error, and per-run all-event conjunction. Zero-duration labels pass only with exactly zero predictions; otherwise relative error is infinite. Report E2E separately; incomplete component sums are never labeled full E2E. Nested spans and host/native clock domains cannot be summed indiscriminately.

Model comparisons are bounded and descriptive. Choose an explicit accuracy/tail tradeoff, disclose model selection on development predictions, and avoid claiming an untouched holdout. Preserve source hashes, fold identities, prediction outputs, and runnable regeneration commands.

## Hardware transfer

Expose relevant CPU/GPU hardware inputs, but distinguish measured reference values from assumptions. Identical hardware does not identify scaling laws. Cross-platform accuracy remains unvalidated until tested against independent hardware measurements. A hardware sensitivity calculation is not evidence that the literal 25% transfer criterion is met.

## Further runs

Recommend new executions only for a named missing event population or an independent hardware validation. Finishing the original 1,088 matrix is not a prerequisite merely to implement and assess D9 using retained evidence. Do not claim that a small additional run guarantees all-event accuracy.

## Event population interpretation

The PDF describes GPU events by input/output/context tokens, so the physical model request is the primary GPU event target. Queue/prefill/decode errors are mechanism diagnostics; logging a phase does not by itself make it an additional mandatory independent D9 event. Similarly, bookkeeping wrappers are not silently counted as CPU operations. The declared evaluation population must include the required CPU operation events and GPU requests with stable boundaries, while retaining component diagnostics separately. It must not be chosen after seeing errors.
